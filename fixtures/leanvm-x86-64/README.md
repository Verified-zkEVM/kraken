# leanVM x86-64 scalar fixture

This bundle reproduces the bare X1 object and the native `stack_offsets` replay for [leanVM #881](https://github.com/leanEthereum/leanVM/issues/881). The replay checks the provisional admission table and stack layout and gives concrete ELF images for the linked-code proofs.

## Build and replay

Use x86-64 Linux with 4 KiB pages and an available fixed-address arena and stack reservation. The commands need Bash, Git, tar, GNU binutils and coreutils, LLD, Python 3.9 or later, rustup and elan. The recorded linker versions are GNU ld 2.42 and LLD 18.1.3.

Run these commands from the Kraken checkout.

```sh
scratch=$(mktemp -d)
git clone https://github.com/leanEthereum/leanVM.git "$scratch/leanVM"
rustup toolchain install 1.96.0 --profile minimal --target x86_64-unknown-none
elan toolchain install leanprover/lean4:v4.36.0
fixtures/leanvm-x86-64/replay.sh "$scratch/leanVM" "$scratch/replay"
```

The output directory must be new. For an object-only run, use `build.sh` with the same two arguments. The source checkout must contain leanVM revision [`db770635a`](https://github.com/leanEthereum/leanVM/tree/db770635a2a26928397e400c4ef1b572df755350). The build takes those source files from Git, so the checkout's branch and working-tree edits have no effect. Set `X1_RUST_TOOLCHAIN` if rustup stores the pinned compiler under a different name. The script verifies the compiler commit and object hash.

`src/` contains the unchanged X1 entry crate, runtime, memory routines, and bare standard-library facade. The build reconstructs their recorded source paths under its output directory and compiles the four leanVM crates from the pinned revision. It uses `x86_64-unknown-none`, target CPU `x86-64`, the target's default relocation model, and fat LTO. The build checks the SHA-256 below for `bare/entry.o`.

```text
d25682c205551c7cc367ac09fba4c97dcbaee751d4813db33c608f009bd0b275
```

The replay produces the ELF images, input sections and relocations, program headers, and entry-stub disassembly under the output directory. All generated files stay in that directory.

## Evidence and proof scope

Each linker builds a static non-PIE image with a read-only stack table and GOT, non-executable stack permissions, and a 4 KiB guard directly below the 64 KiB writable stack. The replay checks the live guard mapping and disjointness of the stack and arena from the ELF load pages, and checks the linked table bytes against the Lean generator.

The replay exercises eight synthetic inputs, including lengths 45, 54, and 94. The single-element input `[0]` reaches the zero-source `BSR` path, and `[63]` checks the maximum shift. The stub aligns the pre-call stack pointer to 16 bytes and checks that the writable interval can hold the stack budget and the 8-byte return address that `call` pushes. After each successful call, it checks the restored stack pointer and all six System V callee-saved general-purpose registers. It also checks the offsets, depth, length, and capacity of the pinned return layout. The capacity word equals the input length for these cases. The proof must establish ownership of the returned allocation.

Negative cases cover a modified entry for length 94, an undersized stack, a 97-element over-budget input, and out-of-range lengths. A fresh process serves each case. The replay stub indexes cases by the selector's ASCII offset from `0`, so `:` selects case 10. GNU ld 2.42 and LLD 18.1.3 each passed all eight cases and rejected the tested mutations and invalid inputs.

Eight separate `break_check` builds use the accepted input of length 94. Each changes one value after `call` returns and before the regular checks run. Six builds clear the upper 32 bits of one saved register. The other builds subtract eight from the restored stack pointer or increment the capacity word. Each ABI rejection must exit with status 1. A failed mapping syscall or a mismatch in the checked offsets, length, or depth exits with status 2.

The 16 KiB budget and all 98 entries generated by `StackTable.lean` are provisional. P6 still needs the input section and resolved-target checks and a proof of linked admission. P7 still needs a proof of the stack bound for every admitted length. The native replay records observed behavior for the concrete inputs above.

Disassemble the two unmodified ELF images from the replay above. GNU ld 2.42 and LLD 18.1.3 produced the same bytes and addresses at the sites below. [leanVM #881, P5](https://github.com/leanEthereum/leanVM/issues/881)

```sh
for linker in ld.bfd ld.lld; do
    objdump -dwC -Mintel "$scratch/replay/$linker.elf" > "$scratch/replay/$linker-panic-disassembly.txt"
done
```

In `stack_offsets`, the branch after the `__rust_alloc` null check is at `0x400153`. The branch after the `__rust_alloc_zeroed` null check is at `0x400226`. Both branch to the call to `panic_nounwind_fmt` at `0x4002df` without preparing panic arguments. The bounds failure calls `panic_bounds_check` at `0x4002da`.

Each linked panic wrapper starts with `55 48 89 e5` (`push rbp` and `mov rbp,rsp`), followed by a direct `call`. The only data accesses before the trap are stack writes.

| Wrapper | Call address | Call bytes | Resolved callee |
| --- | --- | --- | --- |
| `capacity_overflow` | `0x4006a4` | `e8 27 00 00 00` | `panic_nounwind_fmt` at `0x4006d0` |
| `slice_index_fail` | `0x4006b4` | `e8 17 00 00 00` | `panic_nounwind_fmt` at `0x4006d0` |
| `panic_bounds_check` | `0x4006bd` | `e8 0e 00 00 00` | `panic_nounwind_fmt` at `0x4006d0` |
| `panic_nounwind_fmt` | `0x4006d4` | `e8 a7 fe ff ff` | `rust_begin_unwind` at `0x400580` |

Measure the additional stack use from the originating caller's RSP just before its panic call. A direct call to `panic_nounwind_fmt` uses 24 bytes in three writes of eight bytes each. The originating `call` writes a return address. The wrapper pushes RBP and its `call` to `rust_begin_unwind` writes a second return address.

A call through any of the other three wrappers adds one RBP push and one return address for its `call` to `panic_nounwind_fmt`. This path uses 40 bytes in five writes of eight bytes each. The bound for the full execution includes the caller's existing frame and any earlier stack use separately.

The handler's bytes are `0f 0b 0f 0b`. With writable stack space for the calls and pushes, execution reaches the first `ud2` before any access through the unprepared arguments. The host policy makes that instruction a nonaccepting stop.

The standalone executable installs no SIGILL handler. Linux v6.6 resets caught dispositions on `exec`. A user-mode `ud2` enters the invalid-opcode handler, which delivers a forced SIGILL. [Exec setup](https://github.com/torvalds/linux/blob/v6.6/fs/exec.c#L1371) · [Disposition reset](https://github.com/torvalds/linux/blob/v6.6/kernel/signal.c#L537-L555) · [User-mode invalid-opcode entry](https://github.com/torvalds/linux/blob/v6.6/arch/x86/kernel/traps.c#L249-L265) · [SIGILL delivery](https://github.com/torvalds/linux/blob/v6.6/arch/x86/kernel/traps.c#L204-L212) · [Trap dispatch](https://github.com/torvalds/linux/blob/v6.6/arch/x86/kernel/traps.c#L147-L176)

The forced delivery restores the default disposition when SIGILL was ignored or blocked and clears any SIGILL mask bit. Under normal Linux v6.6 delivery, the default action terminates the untraced fixture process. This fatal path adds no signal handler frame to the fixture's user stack. [Forced signal delivery](https://github.com/torvalds/linux/blob/v6.6/kernel/signal.c#L1324-L1368) · [Default fatal action](https://github.com/torvalds/linux/blob/v6.6/kernel/signal.c#L2856-L2892)

The `ud2` at `0x401aed` is inside `stable::quicksort` and has incoming conditional branches at `0x4011f5` and `0x401575`. P8 must prove that separate trap unreachable. P5 still needs a linked-code proof that each declared panic path reaches the handler's first `ud2`, with the stack writes covered on every prefix. The replay exercises normal cases and stub rejections. The panic evidence here comes from disassembly and the cited kernel source.
